# Lessons

- 當使用者先要求保留舊 Demo 功能、後續又釐清正式產品模型時，應以最新且更具體的商業流程為準；先區分「平台使用權」與「活動內記帳單位」，再決定是否保留錢包、儲值或推薦功能。
- 金流尚未串接時，前端 Demo 啟用必須明示「不代表已付款」；正式授權只能由驗證 webhook 的可信後端核發，不能相信瀏覽器付款成功頁。
- 有期限的即時場次到期後，應停止所有新風險（新注、新盤、新推播），但要保留封盤、結算、封存與歷史讀取，避免形成無法善後的未結注單。
- 使用者要求保留原版刺激感時，應先分離「玩家正負分體驗」與「平台建立主持人債權」：可保留任意風險分數、選項數計分與完整參與者報表，但不能把全體淨分的相反數定義成主持人收益或應收應付。
- Firebase 寫入失敗不可一律顯示成「網路錯誤」；前端應區分權限拒絕、場次到期、題目截止、身分驗證與真正離線，並在正式環境用實際建立房間到參與者提交的端對端流程驗證。
- 有倒數與封存的介面必須先判斷終態，再顯示剩餘時間；封存後除 Rules 拒絕寫入外，畫面也要主動切成唯讀並停用輸入，避免「資料已鎖住但看起來仍能操作」。
- BetPanel 的單場期限以「房間建立」為唯一啟動點：建立後立即固定六小時，重新整理或重開只能接續原期限；不要再建議付款後另設延後啟用按鈕，以免偏離使用者確認的產品流程。
